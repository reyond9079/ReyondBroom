# Профили компиляции ReyondBroom с поведением и интерфейсом TrenchBroom

Спецификация и промпт для ИИ агента. Версия 1.0, 6 ноября 2026 года.

Реализовать внутри существующего редактора ReyondBroom совместимый с TrenchBroom редактор и исполнитель профилей компиляции. Один и тот же профиль, карта, настройки игры, инструменты и начальное дерево файлов должны давать одинаковые аргументы запуска, рабочие каталоги, экспорт и файловые операции. Основной диалог должен воспроизводить расположение, размеры, значки, плотность и взаимодействия TrenchBroom. Сохранить доступные кнопки импорта из TrenchBroom.

Это задача на последующую реализацию. При подготовке этой спецификации рабочий код ReyondBroom не изменялся.

## 1. Эталон и границы сравнения

**Эталон TrenchBroom:** последний стабильный релиз на дату исследования — **2026.2**, опубликован 21 августа 2026 года. Тег `v2026.2`, коммит **4c756be1a54a28d921d18c77716a5f170bdc31d0**. Не подменять его плавающей веткой master: её HEAD на момент исследования уже другой.

**Исходное состояние ReyondBroom:** опубликованный **0.5.0-alpha.126**, код сборок **b1291df2957c3e6172097583b8c5d63ff0f3e61e**. Ветка main при исследовании — **27bd45f55a745b1d1a4aae5d0c3ce7b7a6c25822**; последующий коммит меняет только пояснение о `.bspw`, функциональный код совпадает с релизом.

**Платформы:** Windows x64 — обязательная платформа приёмки исходного Windows-профиля; также native Linux x64 и Linux SDL2 x64, которые выпускает ReyondBroom. Сравнивать UI на одной ОС, с одинаковыми DPI, темой, шрифтами и клиентским размером. Windows и Linux имеют разные значения отступов и Qt style; нельзя объявлять Windows UI идентичным по одному Linux-скриншоту.

**Что исследовано непосредственно:** исходники обеих программ; официальный Linux AppImage TrenchBroom 2026.2, запущенный с `--portable`; опубликованный Linux-пакет ReyondBroom alpha126; реальные GUI, режим Test и файловые операции в отдельных тестовых каталогах. Контрольные суммы скачанных архивов проверены. Официальные Windows-иллюстрации руководства прилагаются как дополнительные референсы: точная версия программы на этих иллюстрациях не установлена, они не заменяют актуальный Windows эталон 2026.2.

Совместимость касается подсистемы профилей компиляции, настроек путей и связанного запуска движка. Она не требует переносить весь редактор TrenchBroom, все его игры или его систему сборки в ReyondBroom. На общих поддерживаемых форматах карт экспорт должен соответствовать опциям профиля. Действительно неподдерживаемый формат должен давать конкретную ошибку, а не менять профиль.

## 2. Входной файл пользователя и подтверждённые расхождения

Вложение `CompilationProfiles-original.cfg` — исходный файл пользователя без изменений. В нём **5 профилей, 70 задач**, арифметика `${CPU_COUNT - 1}`, Export Map, Run Tool, Copy Files и Delete Files. В первом VIS задано `.bspw`; флаг `treatNonZeroResultCodeAsError` выключен.

**Не исправлять `.bspw`, расширения, регистр, аргументы, пути или флаги за пользователя.** Пользователь подтвердил, что этот файл работал в TrenchBroom в таком виде. Нестандартное расширение само по себе не является ошибкой импорта. Успешное завершение профиля также не доказывает успешность каждого инструмента, если остановка по ненулевому коду выключена. Не объявлять конкретную причину работоспособности внешнего VIS без запуска той же версии инструмента.

Alpha126 устранил узкий сбой импорта `${CPU_COUNT - 1}`; это не полная совместимость с TrenchBroom. Импорт оригинального файла уже проверен — все 5/70 сохраняются. Новая реализация обязана сохранить этот результат.

### 2.1. Эксперимент с файлами в настоящих редакторах

Создан независимый от игровых компиляторов профиль:

1. Copy Files: `seed.txt` → каталог `copydir`.
2. Rename File: `copydir/seed.txt` → `moved/renamed.txt`.
3. Delete Files: `cleanup/*.tmp`.
4. Copy Files: отсутствующий `missing.bsp` → каталог `no-matches`.
5. Delete Files: отсутствующий `cleanup/missing-file.bsp`.
6. Run Tool: `/bin/echo QA_FILE_TASKS_FINISHED`, остановка по ненулевому коду включена.

Начальное дерево: `seed.txt`, `cleanup/top.tmp`, `cleanup/nested/deep.TMP`, `cleanup/nested/keep.bsp`. Оба редактора получили одинаковые содержимое и последовательность; каталоги были раздельными.

| Проверка | TrenchBroom 2026.2, реально выполнено | ReyondBroom alpha126, реально выполнено |
| --- | --- | --- |
| Копирование и перемещение | Файл оказывается в `moved/renamed.txt` | То же |
| Delete Files `cleanup/*.tmp` | Удалены `top.tmp` и вложенный `deep.TMP` | Удалён только `top.tmp` |
| Копирование отсутствующего `missing.bsp` из существующего каталога | Пустой набор файлов, профиль продолжается | `File tasks accept regular files only.`, профиль остановлен |
| Удаление отсутствующего файла из существующего каталога | Пустой набор, профиль продолжается | До шага не дошёл; по коду точный отсутствующий путь также отклоняется |
| Последний Run Tool | Маркер напечатан, exit 0 | Не запущен из-за шага 4 |
| Test | Дерево и SHA-256 файлов не изменились | Такой режим отсутствует |

Логи и инвентаризации до/после: `tb-file-compile.log`, `tb-file-test.log`, `tb-file-results.json`, `rb-file-compile.log`, `rb-file-results.json` в пакете доказательств.

Вывод по исходникам и эксперименту: Copy Files в TB ищет совпадения **плоско**, Delete Files — **рекурсивно**, сопоставление имени файла — **без учёта регистра**, в том числе в Linux. Это разные правила обхода, их нельзя заменять одним общим «glob в текущей папке». Успех при пустом наборе предполагает существующий каталог поиска; отсутствующий каталог — отдельный случай с ошибкой.

### 2.2. Разбор аргументов

`arguments-probe.cpp` компилирует настоящий `kdl::cmd_parse_args` из зафиксированного TrenchBroom и сравнивает его с циклом `std::quoted` из Linux-ветки ReyondBroom. Это проверка алгоритмов разбора; Windows CreateProcess в этом эксперименте не запускался.

Пример строки параметров: `"C:\Tools\map dir\test.map"`. TB сохраняет обратные слеши в аргументе, Linux-ветка RB получает `C:Toolsmap dirtest.map`. Такие строки нужны для проверки правил экранирования независимо от существования Windows-пути в Linux.

Имеются также различия на пустых кавычках и других пограничных строках. Эталон — фактический `cmd_parse_args` 2026.2 и его тесты, а не предположение о POSIX shell, shlex или CommandLineToArgvW. Лог: `arguments-probe.log`.

## 3. Что сейчас устроено в TrenchBroom

### 3.1. Модель и хранение

Конфигурация компиляции принадлежит **игре**, содержит список профилей, каждый с `name`, `workdir`, `tasks`. Имя может быть пустым и не обязано быть уникальным. Порядок профилей и задач значим.

Есть шесть типов задач: `export`, `copy`, `rename`, `delete`, `tool`, `launchEngine`. `enabled` по умолчанию true. Данные задач типизированы, а Launch Engine хранит `engineProfileId`, ссылающийся на профиль запуска текущей игры.

`CompilationProfiles.cfg` в 2026.2 имеет version 1. `GameEngineProfiles.cfg` также version 1; отсутствующий ID старого профиля запуска при чтении генерируется. Чтение построено на строгом парсере EL, а не просто на JSON. Формат файлов и EL внутри строк — разные уровни, проверить оба. Поля и значения, которые допускает эталонный парсер, не ограничивать произвольным JSON-подмножеством.

Изменения сохраняются на Compile/Test и при закрытии диалога. Удаление последнего профиля оставляет пустой список, штатные профили не восстанавливаются сами. Duplicate копирует профиль, не требует нового уникального имени.

### 3.2. Переменные и выражения

TB использует полноценный EL: типы, арифметику, сравнения, логические и битовые операторы, группировку, строковые значения, массивы, maps, ranges, индексы/срезы, case/switch-выражения и стандартные преобразования типов. Строки `${...}` разбираются как выражения; конечное значение преобразуется в строку по правилам EL.

Базовые переменные: `MAP_BASE_NAME`, `MAP_FULL_NAME`, `MAP_DIR_PATH`, `GAME_DIR_PATH`, `MODS`, `APP_DIR_PATH`. `MODS` — **массив**: сначала default mod, затем enabled mods текущей карты в исходном порядке. Это не строка с одним «активным модом». `MODS[0]` и `MODS[-1]` могут обозначать разные каталоги.

`GAME_DIR_PATH` берётся из настроек пути игры. Пути инструментов — именованные настройки compilationTools текущей игры, например `qbsp`, `vis`, `light`. В коде они входят в CommonVariables и потому доступны также при вычислении workdir; таблица руководства описывает более узкую область Tool. При расхождении ориентироваться на зафиксированный исполняемый код и проверку эталоном.

Рабочий каталог вычисляется в контексте CompilationWorkDirVariables. Затем создаётся контекст задач с `WORK_DIR_PATH` и числовым `CPU_COUNT`. В контексте workdir этих двух переменных нет. CPU_COUNT задаётся как минимум 1, но **выражение** `CPU_COUNT - 1` при CPU_COUNT=1 даёт **0**: отдельного clamp результата в TB нет.

Launch Engine использует более узкий LaunchGameEngineVariables: `MAP_BASE_NAME`, `GAME_DIR_PATH`, `MODS` и пути compilationTools. Не переносить автоматически все переменные компиляции в параметры движка.

### 3.3. Выполнение

Выполняются только включённые задачи, строго по порядку. Контекст запуска фиксирует переменные для конкретного запуска. Run Tool получает интерполированный program и параметры, разобранные `kdl::cmd_parse_args`; QProcess запускается с системным окружением и workdir профиля, stdout/stderr поступают в Output. Промежуточный shell сам собой не запускается.

Для нормального ненулевого exit code остановка зависит от `treatNonZeroResultCodeAsError` (по умолчанию false). Ошибка старта или crash — самостоятельная ошибка. Launch Engine стартует выбранный профиль отдельно от компилятора, без ожидания выхода игры, из каталога executable; неуспешный запуск обрабатывается по `treatLaunchFailureAsError` (по умолчанию false).

Test выполняет интерполяцию, строит и выводит планы задач и наборы файлов, но не экспортирует карту, не запускает инструменты/движок и не выполняет create/copy/rename/delete. Дальнейшие шаги Test не должны предполагать, что предыдущий Export/Copy физически создал файлы.

Диалог немодальный: можно продолжать редактировать карту. Закрытие Compile при активном запуске спрашивает, нужно ли остановить его; отказ оставляет окно и процесс открытыми. Есть Stop, Close, повтор последней компиляции и отдельный Launch.

## 5. Функциональные требования к реализации

### 5.1. Модель, миграция и импорт

Сделать явные типы `ExportMap`, `CopyFiles`, `RenameFile`, `DeleteFiles`, `RunTool`, `LaunchEngine` с TB-полями. Дополнительные данные ReyondBroom хранить отдельно и не терять при миграции. Engine profiles должны иметь стабильные ID, имя, path, parameterSpec и принадлежность игре.

Ранее импортированные профили уже содержат заменённые TB_GAME_ROOT/TB_ACTIVE_MOD. Миграция должна сохранять их работоспособность и резервную копию старого хранения. По такому старому полю нельзя восстановить, было ли исходно `MODS[0]`, `MODS[-1]` или `MODS`; не угадывать. Сохранить legacy aliases для старых записей, при повторном импорте оригинала создавать корректную новую модель. Повторный импорт не обязан дедуплицировать одинаковые имена.

Импорт сохраняет исходные поля, порядок, disabled состояния, флаги и все опции. Не заменять tool path встроенным компилятором и не нормализовывать произвольные строки параметров. Некорректное выражение в отключённом шаге не должно заставлять выбросить весь профиль: оно не исполняется, пока шаг выключен. Диагностика должна указывать профиль/задачу/поле и не скрывать уже прочитанные данные.

Кнопка `Import TrenchBroom profiles...` остаётся в основном Compile. В её диалоге сохранить выбор cfg/каталога, Review import, Import profiles, Cancel и сообщения о результатах; импорт ничего не запускает и не чистит. Поддержать связанные GameEngineProfiles.cfg и настройки compilationTools с явным сопоставлением текущей игре; не считать переменную с пустым значением нормально настроенным executable.

Не утверждать, что TB 2026.2 записывает version 2: чтение версии 2 в нынешнем RB само по себе не доказывает существования такого TB-формата. Имеющуюся поддержку RB не ломать, а известные version 1 проверять по настоящим writer/parser TB.

### 5.2. EL, переменные и пути

Реализовать EL как самостоятельную библиотеку/адаптер, которую используют вычисление workdir, поля задач, Test, подсказки и Launch. При переносе исходников и ресурсов сохранить их лицензии и авторство. Не использовать shell/eval для вычисления `${...}`.

Обязательны все операторы и преобразования зафиксированного TbElLib, а не только арифметика/индексация из входного файла. Перенести или адаптировать семантические тесты Expression/Interpolate/ParseExpression. Отдельно проверить undefined/null, ошибки типов и незакрытые выражения; не заменять ошибки пустой строкой. В UI показывать автодополнение доступных переменных для соответствующего контекста, без подмены исходного текста его вычисленным значением.

`MODS=[defaultMod, enabledMod1, ...]`; порядок брать из текущей карты/ресурсов. Если интерфейс настроек RB пока хранит только один мод, добавить реальное упорядоченное представление, а не подделывать MODS строкой. GAME_DIR_PATH и пути модов разделить, пути к инструментам задавать для игры. Не кодировать `baseq3` в переменной MODS для Quake 1/2/Half-Life.

Сохранить Windows drive letters, UNC, пробелы, Unicode, прямые/обратные слеши в том объёме и с теми правилами, что допускает TB на этой ОС. Относительные пути файловых задач вычислять от workdir. APP_DIR_PATH должен обозначать каталог реально запускаемого приложения в принятом способе упаковки, а не произвольную папку конфигурации. Переезд portable-дистрибутива не должен ломать выражения относительных путей.

Уточнить и воспроизвести значения пустого workdir, относительного workdir и относительного executable через платформенный запуск TB. TB не выполняет глобальный create_directories(workdir) перед всеми задачами: его runner сообщает об отсутствующем каталоге и передаёт выполнение конкретной задаче. Не сохранять нынешнее глобальное создание папки, если оно меняет результат. Создание родителей у Export/Copy/Rename — отдельные действия этих задач.

Windows-путь из Windows-профиля не обязан существовать или быть исполнимым в Linux. Критерий совместимости путей — сравнение на той же ОС и тех же настроенных каталогах, а не автоматическое преобразование `D:` в Linux или замена чужих инструментов встроенными.

### 5.3. Файловые задачи

**Copy Files:** всегда target directory по семантике TB; `source` — имя или filename mask в конкретном исходном каталоге, flat search, только файлы. Папка назначения создаётся рекурсивно, файлы перезаписываются как в Disk::copyFile. Проверить копирование файла в собственный каталог и одинаковые source/target по фактическому эталону; нынешний специальный skip в RB не считать автоматически правильным.

**Rename File:** точный source, target file path в UI, создание родительского каталога. Повторить фактическое поведение Disk::moveFile, включая существующий target, target directory, перемещение между дисками/FS и ошибки. Руководство и низкоуровневый Disk::moveFile имеют различия на некоторых edge cases; реальные результаты эталона на нужной ОС важнее догадки по названию поля. Не обещать перенос между FS, если эталон его не делает.

**Delete Files:** recursive traversal от parent directory заданного target, совпадения по filename, только файлы; регистр сравнения не зависит от ОС. Рекурсивность касается не только строки с `*`: даже точное filename ищется matcher-ом при recursive traversal. Не удалять сами каталоги как замену этому алгоритму. Удалять промежуточные `.prt`, `.pts`, `.lin`, `.log`, `.texinfo` и другие файлы именно по заданным пользователем шагам, не вводить свой список «лишних» расширений.

Отсутствие совпадений в существующем исходном каталоге — корректный пустой набор Copy/Delete. Отсутствующий каталог поиска, ошибки доступа, readonly, symlink/junction и ошибки отдельного файла проверять дифференциально с TB. В источнике Disk::find разрешён обход directory symlink; циклы/ошибки доступа не подменять обещанием транзакции. Не объявлять атомарность всей файловой партии: TB обходит и обрабатывает файлы последовательно, а нынешний RB заранее валидирует весь batch.

Совместимый режим не должен самовольно запрещать допустимое в TB неразрушающее копирование текущей `.map` только потому, что source совпал с открытой картой. Для явно заданных пользователем операций Export/Copy/Rename/Delete воспроизвести TB-семантику и отразить любые оставшиеся отличия в приёмке. Импорт и Test ни при каких обстоятельствах не исполняют эти операции. Проверять изменяющие файлы сценарии только в тестовых каталогах.

### 5.4. Экспорт карты

Поддержать `target`, `stripTbProperties`, `stripEntityPattern`, `entityToAdd` со всеми key/value парами. UI Add Entity редактирует classname, origin/angle экспортируемого экземпляра берутся с камеры, как у TB. Не ограничивать импорт только classname, если cfg содержит дополнительные свойства.

Отключённые от экспорта слои исключаются. Удаление `_tb_` свойств и сущностей по classname GLOB применяется только к экспортируемому результату. Внутренняя карта/undo/сохранённый исходник не должны меняться как побочный эффект подготовки отдельного compile copy. Экспортировать текущее состояние редактора, включая несохранённые правки, в поддерживаемом формате карты.

Текущий `runPrepareExport` в RB дополнительно преобразует модели/contents, генерирует WAD/материалы, stage-ит ресурсы и спрашивает о missing textures. Разделить эту подготовку и собственно совместимый TB-export. Не удалять возможности обычного Compile/preview RB; не применять незаявленное преобразование геометрии/сущностей к профилю TB. Проверить интеграцию с q1CompilerWads, generated models, shaderPackStage, Q2 contents и Half-Life WAD3. Если для игрового формата требуется подготовка ресурсов, сохранить её явно и доказать, что она не меняет контракт профиля.

### 5.5. Процессы, ошибки и управление

Один раз разбирать parameters в массив argv по правилам `kdl::cmd_parse_args`. На Windows сериализовать этот argv для CreateProcess корректно и проверять аргументы в настоящем дочернем probe-процессе; текущий raw parameters без общего разбора не достаточен. Не запускать shell, если пользователь явно не выбрал shell executable.

Сохранить работоспособность существующих bundled compiler presets, BSP preview и канала управления preview. Они должны использовать адаптеры к общему runner, а не менять семантику импортированного tool. Старое перенаправление несуществующего fteqw64.exe на bundled engine нельзя применять к произвольному пользовательскому executable в TB-профиле.

Включённый tool с обычным exit code !=0 и выключенным Stop on nonzero error code продолжает профиль. Ошибка запуска и crash не маскируются этим флагом. В Linux лог должен содержать числовой код/причину, а не только `Tool failed.`. Launch Engine не ждать завершения игры; поддержать ID, живое обновление списка при редактировании launch profiles и правильную область переменных. Ошибка Launch с выключенным Stop on launch failure записывается в Output и позволяет перейти дальше, не выключая задачу навсегда.

Повторить поведение Stop/Close/Escape и закрытия главного окна относительно активного запуска; фоновые процессы и читаемый вывод не должны зависать. Сохранить имеющиеся средства остановки дерева процессов RB и не оставлять игровые preview-процессы зомби. Изменение выбранного профиля во время компиляции не должно менять уже запущенную последовательность. Re-run использует предыдущий профиль, как TB, и пересчитывает переменные для текущей карты по правилам эталона.

Не вводить глобальные запреты на Run Tool только по наличию подстроки `q3map2` в path произвольного executable: допустимость настоящего профиля проверять по реальным данным и инструменту.

### 5.6. Режим Test

Общий pipeline с Compile, отдельный флаг test/dry run. Те же интерполяция, enabled, engine lookup, наборы файлов и ошибки подготовки, но ни одной операции записи/создания каталогов и ни одного запуска процесса. Вывести workdir, экспортный target, executable/argv, source/target и выбранные к удалению файлы.

Не создавать виртуальные результаты предыдущих шагов так, будто это реальные файлы: реальный TB-Test ищет Copy/Delete в существующем на момент Test дереве. Поэтому Test профиля с Export+Copy может показывать пустой Copy. Проверить дерево, содержимое и отсутствие новых каталогов до/после; одной надписи «Test» недостаточно.

## 6. Интерфейс

### 6.1. Основная компоновка

Заменить содержимое нынешнего Compile / Launch на диалог **Compile**, остающийся частью настоящего native редактора. Не сдавать HTML-макет или внешний launcher вместо рабочего окна.

Сверху: **Profiles** слева и **Details** справа. В Profiles — список с жирным именем и строкой `N tasks`, выделение, обрезка длинных имён как в TB. Внизу слева штатная mini-toolbar с `+` и `−`. Контекстное меню профиля: Duplicate, Remove. Пустой список и отсутствие выбора имеют те же подсказки/disabled состояния.

В Details сверху две компактные строки: Name и Working Directory, метки слева, поля справа. Ни `Engine launch profile`, ни общая dropdown-смена типа задачи не должны занимать место между этими полями и задачами. Список задач прокручивается и занимает остаток верхней области, не фиксированные 200 px.

Нижняя mini-toolbar Details: `+`, `−`, `↑`, `↓` в этом порядке. Управляет выделенной задачей, правильные disabled состояния на границах. `+` открывает меню в порядке TB: Export Map, Copy Files, Rename File, Delete Files, Run Tool, Launch Engine. Новая задача вставляется после выбранной; если выбора нет, в конец. Контекстное меню задачи: Move Up, Move Down, разделитель, Duplicate, Remove.

Под верхней областью — **вертикальный splitter** и Output. Начальные размеры/перетаскивание повторить по эталону; исходный код задаёт sizes {2,1}, но фактическая геометрия зависит от minimum/sizeHint карточек. Не выдавать абстрактное «две трети» за измеренные координаты.

Внизу отдельная полоса кнопок: Launch..., Stop, Test, Compile, Close и Running label с теми же расположением и выравниванием на целевой ОС. Compile — default action. Не заменять их Run profile / Copy log. Output имеет штатные выделение/копирование, scrollbar, context menu и Clear.

### 6.2. Поля и состояния карточек

| Карточка | Поля в исходном порядке TB |
| --- | --- |
| Export Map | File Path; Strip Entities (placeholder `enter GLOB pattern`); Add Entity (`enter classname`); checkbox `Strip TrenchBroom specific entity properties` |
| Copy Files | Source File Path; Target Directory Path |
| Rename File | Source File Path; Target File Path |
| Delete Files | File Path |
| Run Tool | Tool Path и кнопка `...` справа в этой строке; Parameters; checkbox `Stop on nonzero error code` |
| Launch Engine | Engine Profile; checkbox `Stop on launch failure` |

Каждая карточка имеет свой заголовок, разделители и **один checkbox enabled слева от формы**, центрированный по вертикали содержимого. Это не отдельная строка `Enabled` над карточкой. Не рисовать Remove/Move up внутри каждой карточки. Поля путей и parameters моноширинные. Имя профиля и обычные описания используют обычный UI-шрифт. Tooltips, placeholder, Tab-порядок, selection, фокус, clipboard, inline editing, autocompletion и действия мышью должны соответствовать TB.

Не изобретать новые горячие клавиши: штатные Run/Compile/Launch/Rerun в ActionManager 2026.2 не имеют default QKeySequence. Проверить локальные клавиши диалога, Enter/Escape и редактирования, сохранить пользовательские bindings RB там, где они не конфликтуют с целевым поведением. Действия редактирования полей не должны попадать в редактор карты.

### 6.3. Метрики и значки

Факты из исходников TB:

* Начальный клиентский размер Compile — **800×600 DIP**, minimum **600×300 DIP**. Минимум Profiles-панели **200×200 DIP**; фактическая ширина не фиксирована в 200 и зависит от списка.
* Штатные Add.svg, Remove.svg, Up.svg, Down.svg имеют базовый размер **16×16**. Внешний размер QToolButton зависит от Qt style; нельзя считать его равным размеру иконки.
* Windows: WideHMargin=8, MediumHMargin=6, NarrowHMargin=4; WideVMargin=8, MediumVMargin=4, NarrowVMargin=2. Нижняя полоса: left/right=7, top/bottom=10 DIP.
* Linux: WideHMargin=8, MediumHMargin=4, NarrowHMargin=2; вертикальные 8/4/2. Нижняя полоса: left/right=8, top/bottom=10 DIP.
* У профиля header-форма: medium horizontal margins, wide vertical margins, vertical spacing=0. У форм задач: wide margins=8, vertical spacing=4. Mini-toolbar имеет narrow left/right margins, narrow spacing, vertical margins=0.
* Внешние размеры содержимого, высоты строк/заголовков, шрифты, selected/hover/disabled рисование и реальные позиции footer надо снимать с исполняемой сборки той же ОС. Имитация общим modern ImGui style с округлыми крупными кнопками не соответствует задаче.

В приложенном Linux-снимке `tb-compile-customer-800x600.png` клиент ровно 800×600: вертикальная граница Profiles/Details на x≈256, splitter на y≈442, нижние кнопки на y≈566. Это измерения **данного** снимка с длинными именами пяти профилей, не универсальные константы. Они нужны для прямого воспроизведения именно этого состояния. Не переносить их на Windows без измерения.

Воспроизвести исходные значки и толщину штрихов, не заменять `+`, `−`, стрелки похожими Lucide-символами по вкусу. Если используются оригинальные SVG, сохранить авторство/лицензии. Установить стиль только для Compile и связанных окон; не переделывать весь UI ReyondBroom ради одного диалога.

### 6.4. Обязательное исключение — импорт

**Не удалять кнопки импорта профиля из TrenchBroom.** Это согласованное дополнение к эталону, а не повод перераспределить весь Compile.

Разместить `Import TrenchBroom profiles...` отдельной компактной строкой в Profiles **над** штатной нижней mini-toolbar. `+ / −`, Details, splitter и footer остаются в своих эталонных позициях; сокращается только полезная высота списка Profiles на строку импорта. При узкой колонке допустимо обрезать текст, но полный текст доступен в tooltip, кнопка видна и работоспособна. Визуальное сравнение исключает только эту добавленную строку и соответствующее изменение высоты списка.

Сохранить Review import / Import profiles / Cancel в диалоге импорта, browse и диагностические сообщения. Нельзя спрятать единственный способ импорта в недоступный старый экран. Настройки tool paths и специфические расширения RB вынести в настройки игры или отдельную дополнительную панель, не вклинивая их между штатными карточками и toolbar.

### 6.5. Проверка идентичности

До реализации снять актуальный Windows TB 2026.2: 800×600 и увеличенный диалог, DPI 100/150/200%, темная/светлая тема при поддержке эталоном. На Linux сделать те же пары для используемого Qt style. Зафиксировать ОС/build, размер клиента, DPR, тему, UI/mono font, масштаб и fixture. Не сравнивать снимки с разными шрифтами или размерами окна как доказательство совпадения.

Состояния: пустой список; выбранный профиль; все шесть карточек; disabled task; выбранная задача и границы move; меню +; контекстные меню; автодополнение; файл выбора tool; engine profile selector; активная компиляция; Test output; ошибка; закрытие во время запуска; импорт. Проверить прокрутку длинного профиля на 14 задач и сохранение фокуса при изменениях.

Для каждой пары TB/RB приложить bounding boxes, таблицу размеров, наложение и diff. В одинаковых условиях расположение/размеры должны совпадать в DIP; допускается только растровое расхождение сглаживания и округление до 1 physical pixel на дробном DPR. Другие отличия не называть «идентичным UI». Маска исключений — только OS window chrome и указанная строка импорта; нельзя маскировать всю форму или footer.

## 9. Готовый промпт исполнителю

Ты работаешь над ReyondBroom. Прочитай эту спецификацию целиком, затем файлы текущей реализации и зафиксированные исходники TrenchBroom 2026.2. Твоя задача — реализовать полную совместимость профилей компиляции и воспроизвести их интерфейс внутри native редактора, сохранив кнопки импорта TrenchBroom.

Используй TrenchBroom commit 4c756be1a54a28d921d18c77716a5f170bdc31d0 как проверяемый oracle. Не считай alpha126 полной совместимостью: там устранён лишь отдельный сбой CPU_COUNT-1. Не редактируй исходный пользовательский cfg и не исправляй `.bspw` по своему предположению. Не сохраняй MODS как единственную строку, не вычисляй EL через shell и не добавляй частные regexp-исключения вместо языка.

Начни с oracle fixtures и актуального Windows/Linux UI atlas. Реализуй модель/миграцию/per-game settings, полную EL с корректными scopes, пути, шесть задач, recursive Delete/flat Copy, argv, error policies, Test и lifecycle по разделам 4–5. Затем собери компактный Compile по разделу 6, включая исходные мини-панели, карточки, подписи, tooltips, autocomplete и состояния. Из всех визуальных отличий заранее разрешена только строка импорта, описанная в разделе 6.4.

Работай по этапам раздела 7, доказывай результат матрицей A01–A20/U01–U03. Исходный профиль должен оставаться 5/70 до и после сохранения и перезапуска. Сравнение только по скриншоту или успешному импорту недостаточно: нужны реальные файловые/процессные результаты. Не заменяй рабочий native UI картинкой/HTML. Сохрани интеграцию существующего BSP preview и bundled compiler flows через адаптеры.

В результате предоставь PR, миграционную заметку, тесты и воспроизводимые probes, лог сравнения обоих редакторов, реальный UI atlas с геометрией/diffs, результаты по каждой строке приёмки и точный список оставшихся несовпадений. Задачу можно закрывать только когда требования функциональной совместимости и идентичности интерфейса выполнены; оставшийся неподтверждённый Windows UI означает, что соответствующая приёмка ещё не завершена.
